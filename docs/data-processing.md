# Data loading and processing

How Meshdex moves and processes data efficiently. Every technique used in the code gets an entry here: **what** it is, **where** it lives, **why** this way (and what the alternative was), and the **benchmark** that backs it. Entries are added in the same commit as the code that introduces them.

## Principles

- **Bytes never pass through services that don't need them.** Large files go browser → S3 directly; services exchange ids and metadata.
- **Stream, don't buffer**, unless a library needs the whole object in memory — then say so and bound it.
- **Bounded concurrency everywhere.** Every fan-out (S3 parts, ingest downloads, worker jobs, DB writes) has an explicit limit.
- **Backpressure over queues in memory.** A slow consumer slows the producer (pause the Kafka consumer, stream `highWaterMark`) instead of growing a buffer.
- **Batch at boundaries.** Fetch many by id in one call, insert many rows in one statement, embed many images in one model call.
- **Measure before and after.** Claims about performance link to a report in `docs/benchmarks/`.

| Two-stage pipeline with a bounded queue     | `ingest/src/import/import.service.ts`, `ingest/src/tasks/bounded-queue.ts`                          | Pack (CPU, disk) and upload (network) overlap: P packers → queue of Q → U uploaders. The queue is the only buffer, so at most P + Q + U GLBs are in memory whichever stage is slower: a full queue makes packers wait (`push`), an empty one makes uploaders wait (`take`), the same backpressure `stream.pipeline` gives bytes, applied to whole items. Parts of one model go sequentially as zero-copy `subarray` views (concurrency is across models). Imported models are appended to a JSON Lines state file (one small append per model, a crash at worst cuts the last line, which is skipped), so re-runs don't create duplicates. Limit: the bound counts models, not bytes; the 1k catalog has a 958 MB model (`pine_tree_01`), so a byte budget is the next step before importing everything                                                                                          | Unit test: 12 models with uploads as the bottleneck, P = Q = U = 1 → never more than 3 GLBs held. Live (P = 2, Q = 4, U = 4, local): 8 models, 6.8 MB in 183 ms, peak RSS 209 MB; re-run imported only the 2 missing models, third run uploaded nothing (2 ms). [Import benchmark](benchmarks/ingest-import.md) (P = 2, Q = 4, U = 4, 5 runs): 1k50 83 MB/s, 4k10 134 MB/s, upload-bound in both (uploaders busy 87–93 %). [Upload-concurrency sweep](benchmarks/ingest-upload-concurrency.md): U = 1/2/4/8 → 40/59/75/88 MB/s, each doubling helps less (1.49×, 1.27×, 1.17×) because one upload slows from 32 to 103 ms on a shared local stack; default stays 4 until measured against networked storage. A sweep of Q is still to do |

| Conditional upsert as a per-asset guard     | `embedded_versions` (migration 002), `EmbeddingsRepository.save_versions`                           | One row per (model, asset), upserted with `ON CONFLICT … DO UPDATE … WHERE stored.version_number <= EXCLUDED.version_number RETURNING asset_id`: the row lock serialises concurrent writers of one asset, the condition rejects out-of-order versions, and `RETURNING` says which versions to write.
