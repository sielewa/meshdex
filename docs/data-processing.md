# Data loading and processing

How Meshdex moves and processes data efficiently. Every technique used in the code gets an entry here: **what** it is, **where** it lives, **why** this way (and what the alternative was), and the **benchmark** that backs it. Entries are added in the same commit as the code that introduces them.

## Principles

- **Bytes never pass through services that don't need them.** Large files go browser → S3 directly; services exchange ids and metadata.
- **Stream, don't buffer**, unless a library needs the whole object in memory — then say so and bound it.
- **Bounded concurrency everywhere.** Every fan-out (S3 parts, ingest downloads, worker jobs, DB writes) has an explicit limit.
- **Backpressure over queues in memory.** A slow consumer slows the producer (pause the Kafka consumer, stream `highWaterMark`) instead of growing a buffer.
- **Batch at boundaries.** Fetch many by id in one call, insert many rows in one statement, embed many images in one model call.
- **Measure before and after.** Claims about performance link to a report in `docs/benchmarks/`.

| glTF → GLB packing in memory                | `ingest/src/packing/packing.service.ts`                                                             | Poly Haven serves `.gltf` + `.bin` + textures; asset-service accepts one GLB. `@gltf-transform/core` needs the whole model in memory, which is acceptable because the resolution (1k default) and the pipeline bound it. | Two-stage pipeline with a bounded queue     | `ingest/src/import/import.service.ts`, `ingest/src/tasks/bounded-queue.ts`                          | Pack (CPU, disk) and upload (network) overlap: P packers → queue of Q → U uploaders. The queue is the only buffer, so at most P + Q + U GLBs are in memory whichever stage is slower: a full queue makes packers wait (`push`), an empty one makes uploaders wait (`take`), the same backpressure `stream.pipeline` gives bytes, applied to whole items. Parts of one model go sequentially as zero-copy `subarray` views (concurrency is across models). Imported models are appended to a JSON Lines state file (one small append per model, a crash at worst cuts the last line, which is skipped), so re-runs don't create duplicates. Limit: the bound counts models, not bytes; the 1k catalog has a 958 MB model (`pine_tree_01`), so a byte budget is the next step before importing everything | Unit test: 12 models with uploads as the bottleneck, P = Q = U = 1 → never more than 3 GLBs held. Live (P = 2, Q = 4, U = 4, local): 8 models, 6.8 MB in 183 ms, peak RSS 209 MB; re-run imported only the 2 missing models, third run uploaded nothing (2 ms). [Import benchmark](benchmarks/ingest-import.md) (P = 2, Q = 4, U = 4, 5 runs): 1k50 83 MB/s, 4k10 134 MB/s, upload-bound in both (uploaders busy 87–93 %); a sweep of U and Q is still to do |
| Recorded runs with stage waits              | `ingest/src/runs/` (`RunProbe`, `RunsService`), `ImportService` (`--record`, `--label`)             | Benchmarks are built from recorded data, not numbers copied from logs: each run writes one JSON file (options, machine, wall/CPU time, sampled peak RSS/heap/ArrayBuffers, event-loop delay p50/p99/max, throughput). Event-loop delay is measured with a 1 ms `monitorEventLoopDelay` minus its resolution, because synchronous packing on the main thread delays every other callback, uploads included. Per-stage busy time plus two waits locate the bottleneck without a profiler: packers blocked on a full queue → uploads are slower; uploaders idle on an empty queue → packing is slower                                                                                                                                                                                                      | Live (10 models, 1k, P = 2, Q = 4, U = 4, local, M4): 10.6 MB in 241 ms (43.9 MB/s); packers blocked 143 ms vs. uploaders idle 54 ms, queue peaked at 4 → upload-bound; event-loop delay p99 4.9 ms, max 6.7 ms; peak ArrayBuffers 73.5 MB for 10.6 MB of GLB (packing holds source files, document and output at once)                                                                                                                                      |
| Packing in worker threads (experiment)      | `ingest/src/tasks/worker-pool.ts`, `ingest/src/packing/workers/pack.worker.ts`, `--pack-in-workers` | Packing (file reads, JSON parsing, buffer copies) moves off the main thread, one worker per pack slot, running the same `PackingService`; the GLB comes back by transferring its `ArrayBuffer` (no copy). The cost: each worker is a separate V8 isolate (memory, start-up time), and requests and manifests are structured-cloned. `peakArrayBuffersBytes` counts the main thread only, so in this mode RSS is the memory figure to compare                                                                                                                                                                                                                                                                                                              | [Report](benchmarks/ingest-import.md) (5 runs per mode, ABBA order, local, M4), main → workers medians: 1k50 786 → 965 ms, 4k10 601 → 798 ms; CPU +60 % / +116 %; peak RSS +140 MB; event-loop delay max 22.9 → 5.3 ms (1k50). Upload is the bottleneck, so the workers' start-up (~0.2 s per run) is pure cost here: main-thread packing stays the default. Stored bytes identical to main-thread packing                                                   |
