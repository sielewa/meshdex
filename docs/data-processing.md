# Data loading and processing

How Meshdex moves and processes data efficiently. Every technique used in the code gets an entry here: **what** it is, **where** it lives, **why** this way (and what the alternative was), and the **benchmark** that backs it. Entries are added in the same commit as the code that introduces them.

## Principles

- **Bytes never pass through services that don't need them.** Large files go browser → S3 directly; services exchange ids and metadata.
- **Stream, don't buffer**, unless a library needs the whole object in memory — then say so and bound it.
- **Bounded concurrency everywhere.** Every fan-out (S3 parts, ingest downloads, worker jobs, DB writes) has an explicit limit.
- **Backpressure over queues in memory.** A slow consumer slows the producer (pause the Kafka consumer, stream `highWaterMark`) instead of growing a buffer.
- **Batch at boundaries.** Fetch many by id in one call, insert many rows in one statement, embed many images in one model call.
- **Measure before and after.** Claims about performance link to a report in `docs/benchmarks/`.

## Techniques

| Keyset (cursor) pagination                  | `assets_created_at_id_idx` (`asset-service/src/database/schema/assets.table.ts`), `ListAssets` | `OFFSET n` reads and discards `n` rows, so each page gets slower and pages shift when rows are inserted; a cursor `(created_at, id) < (…)` jumps straight into the index. The index's NULLS order must match the query's (`DESC` = `NULLS FIRST`), otherwise Postgres sorts in memory even on `NOT NULL` columns                                                                                                                                                                                         | `EXPLAIN`: `Index Only Scan` with no `Sort` node (verified locally); timing vs. offset in Stage 4                                                                                                                                |
| Connection pool as a per-pod budget         | `asset-service/src/database/database.module.ts`                                                | One `pg.Pool` per process; total connections = pool max × replicas, which must stay below Postgres' `max_connections` when the service scales out                                                                                                                                                                                                                                                                                                                                                        | —                                                                                                                                                                                                                                |
| Partial index for the outbox relay          | `outbox_unpublished_idx` (`outbox.table.ts`)                                                   | The relay only scans unpublished rows; indexing just those keeps the index tiny however large the table grows                                                                                                                                                                                                                                                                                                                                                                                            | —                                                                                                                                                                                                                                |
| Direct-to-storage multipart upload          | `asset-service/src/assets/upload.service.ts`                                                   | File bytes go client → object storage over presigned part URLs; services only exchange ids, so a 512 MiB upload costs the service a few KB. Parts allow parallel transfer and resuming (`GetUploadPartUrls` re-signs only the missing parts); part size is decided by the server (S3: ≥ 5 MiB, ≤ 10 000 parts)                                                                                                                                                                                           | E2E: 20 MiB in 2 parts against SeaweedFS (local); part size vs. throughput in Stage 4                                                                                                                                            |
| Idempotent completion across two systems    | `UploadService.complete`                                                                       | No transaction spans storage and DB, so each step tolerates a retry: an already-completed storage upload is verified with HEAD (size must match the declared one), and a conditional `UPDATE … WHERE status = 'uploading'` lets exactly one call write the outbox event                                                                                                                                                                                                                                  | E2E: two `CompleteUpload` calls → one outbox event                                                                                                                                                                               |
| Batch reads without N+1                     | `AssetViewsRepository.findByIds`, `TagsRepository.linkToAsset`                                 | Assets, their current versions (`DISTINCT ON`) and tags are loaded in 3 queries for any number of ids; tags are linked with 3 statements for any number of tags                                                                                                                                                                                                                                                                                                                                          | —                                                                                                                                                                                                                                |
| Request-scoped batching (DataLoader)        | `gateway/src/assets/asset-loader.factory.ts`                                                   | Every `asset(id)` resolved within one GraphQL request is collected and sent as one `BatchGetAssets` call (split at the RPC's 100-id limit), and repeated ids are served from the loader's cache: N fields cost 1 RPC instead of N. One loader per request, created in the GraphQL context factory — a shared cache would serve stale data (and, with auth, data across users), and a REQUEST-scoped provider would make every dependent resolver request-scoped                                          | E2E (`gateway/test/graphql-api.spec.ts`): 4 lookups in one query → 1 RPC with 3 ids                                                                                                                                              |
| Batched presigned downloads                 | `asset-service/src/downloads/downloads.service.ts` (`GetOriginalDownloadUrls`)                 | File bytes go storage → browser directly; the service only signs URLs. Signing is local HMAC (no storage request), the version lookup is one primary-key query for up to 100 ids, and the RPC is batched so a GraphQL DataLoader asks once per request, not once per asset (no N+1). Versions without a complete original are left out instead of failing the batch                                                                                                                                      | E2E (local SeaweedFS): 3 ids → 1 URL, downloaded bytes identical, tampered or missing signature → 403                                                                                                                            |
| Prefetch only up to a loading boundary      | `web/src/app/assets/[id]/loading.tsx`, static `metadata` in `page.tsx`                         | Next.js prefetches every link in the viewport. For a dynamic route it renders up to the nearest `loading.tsx`, but still runs `generateMetadata`; fetching the asset there made one grid view cost one gateway call (and one URL signature) per visible card. The data now loads only on navigation                                                                                                                                                                                                      | Measured with gateway request logs: grid view 13 → 1 gateway calls; opening an asset +1                                                                                                                                          |
| Resumable multipart upload from the browser | `web/src/features/upload/` (`MultipartUploader`, `runWithConcurrency`, `putPart`)              | The file is cut with `Blob.slice()` (lazy, streamed from disk), parts go straight to object storage over presigned URLs through a bounded pool (4 in flight), so browser memory and open connections stay flat for any file size. XHR because only it reports upload progress. Transient failures retry with exponential backoff and full jitter; a 403 renews that part's URL. Stored parts and their ETags are kept in localStorage, so after a closed tab only missing parts are sent                 | Browser E2E (local SeaweedFS, 5 MiB parts): 9.4 MB file → 2 parallel PUTs, asset viewable; unit tests for concurrency limit, resume, retries and cancel; throughput vs concurrency in Stage 4                                    |
| Streamed download with MD5 on the fly       | `ingest/src/cache/model-cache.service.ts` (`writeFile`), `ingest/src/fetch/fetch.service.ts`   | Each file goes socket → hash → disk through `stream.pipeline`: never buffered, read once, and backpressure reaches the socket when the disk is slower. Bytes land in `<file>.part` and are renamed only when size and MD5 match the API listing, so the cache never holds a corrupt file; an interrupted run re-downloads only missing files, and models whose `files_hash` is unchanged are skipped without a request. At most 4 models in flight (the API is someone else's), retries with full jitter | Live (Poly Haven, 1k): 3 models, 15 files, 2.3 MB in 0.67 s; re-run 0 downloads in 0.11 s; deleted texture → 1 file re-downloaded. Unit tests: chunked hashing, truncated/failed stream leaves no file, concurrency cap, retries |
